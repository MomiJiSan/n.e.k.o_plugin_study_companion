## 1. 一句话定位

Cognitive Evidence Engine 不是第二个私人教练，也不是第二套掌握度系统。

它只负责从经过服务端验证、绑定到审定目录或已有知识图谱 topic 的结构化答题中，形成可验证、可重建、可撤销的错误机制假设，并向 Coach Planner 提交带同 topic 诊断、修复、迁移或保持意图的候选；选哪个知识点和最终是否采用始终由 Coach Planner 一次决定。

当前版本有两层能力边界：

> 在链式法则知识点内，对“遗漏内层导数”这一具体错因，安全完成“确认—修复—迁移验证”。

此外，除已有专用审定目录外，经知识图谱存储验证的 topic 可以使用三个保守的通用错误机制做 Shadow 提取；这些通用假设没有 Active 蓝图，不能触发认知干预题。

V2.0 的终点是 `monitored`。V2.1 只增加跨天保持、`resolved` 和复发闭环；V3 当前只启动 Shadow 策略效果归因底座，在线教学策略个性化尚不实施。

### 2.3 PR #84 可观测性与自动化闭环验收

PR #84 已完成三阶段方案中的工程部分：

- 阶段 A：新增只读 SQLite collector 和健康 CLI，聚合 extraction queue、projection、outbox、episode、obligation、claim、control 与 version set；
- 阶段 B：新增临时数据库场景运行器，覆盖 resolved、relapse、普通错误重排、控制中断、outbox 失败隔离、重启重建、同秒与乱序、lease fencing、未知版本、旧库副本迁移、retention 轮换、答题窗口和全部功能关闭等 14 个场景；
- 阶段 B：通过 Cognitive Off/On 双数据库对照验证 FSRS、Mastery、课程进度、错题状态和普通 attempt/evaluation 不被认知层越权修改；
- 阶段 C：在现有 pytest 后运行认知 V2 验收，并无论成功失败都上传 JSON/Markdown 报告；任一硬性不变量失败时返回非零；
- 离线检查无法得知当前内存配置时返回 `runtime.mode=unknown`；`runtime.mode` 与 `health.status` 保持两个独立维度；
- 健康检查只能报告当前聚合状态，不能声称历史上 `ownership_violations=0`；“未越权”结论只能由 A/B 自动验收给出。

PR #84 没有修改 `StudyStore`、Planner、答题提交、认知 worker 的生产逻辑，也没有新增数据库 schema、运行时后台任务、UI、远程遥测、通知或大屏。GitNexus 变更检测确认最终审查修正未进入生产执行流。

真人实测证据目前已覆盖 `evidence → probe → repair → transfer_check → monitored → retention_check → resolved` 的真实 UI 技术链，其中 question/attempt 账本、认证 evaluator 元数据、episode、obligation、claim、satisfaction 和 outbox 均已只读核验。该证据是在认证修复 `054aee9` 已 fast-forward 合并到 `main` 并安装后取得；本次文档快照以 `6fddbcc` 为权威主线，`3621d26` 是复测启动基线，`054aee9`、`cb2c269`、`420a3c1` 均为通向 `6fddbcc` 的历史节点。`retention_check → resolved` 仍依赖开发态时间前移，且迁移题答案曾由助手告知用户，因此这份证据只证明封闭链路可用，不能证明自然跨天保持或完全独立的人体教学效果。在该保持取证完成时 relapse 仍为 `NOT_EVALUATED`；后续受控 relapse 技术链和自然观察基线见第 26 节。

## 3. 为什么要做这个引擎

现有学习系统已经能够回答：

- 接下来学哪个知识点；
- 某个知识点掌握度如何；
- 哪一天应该复习；
- 哪道错题需要重做；
- 今天的目标和习惯是否完成。

但这些状态不能稳定回答：

> 用户为什么会在同一个知识点上反复出错，以及应该用什么方式验证和修复这个具体错因。

认知引擎补充的是“错误机制证据”，例如：

- 用户是否只求了外层函数导数，遗漏了内层导数；
- 用户是否知道要使用链式法则，但内层函数求导错误；
- 用户是否把复合结构误当成乘积结构。

这些结论必须是局部的、可证伪的、带来源的、可被用户否认或删除的，不能演变成“你数学能力差”“你注意力不集中”之类人格化标签。

## 4. 所有权边界

| 状态或决策 | 唯一所有者 | 认知引擎权限 |
|---|---|---|
| 知识点选择与 `eligible_topics` | Coach Planner | 只能提交候选 |
| FSRS 复习时间 | FSRS | 只提供 `not_before` / `due_by` |
| 知识点掌握度 | Mastery | 只读 |
| 错题生命周期 | Wrong Question | 只引用，不修改 |
| 课程进度与 scope | Learning Plan | 只校验 revision |
| hypothesis、episode、retention | Cognitive Evidence Engine | 完整拥有 |
| 最终答题 verdict | Evaluator | 认知 reducer 只能消费 |
| 最终下一学习行动 | Coach Planner | 最终决定 |
| 用户控制 | 用户 | 必须立即服从 |

认知引擎只提交带认知字段的 `LearningActionCandidate`。`learning_intent`、`hypothesis_target`、通用 `cognitive_strategy`、兼容字段 `repair_strategy` 和 `obligation_refs` 只能作为候选内容，由 Planner 在所有权与 revision 校验后决定是否进入最终 `QuestionPlan`；认知引擎不得在 Planner 决策后再修改计划。

认知引擎不得修改：

- `target_topic`
- `selection_reason`
- `eligible_topics`
- `learning_plan_id` 与 revision
- `scope_key` 与 revision
- `origin_wrong_question_id`
- 难度所有权
- FSRS due time
- Mastery
- 课程进度
- 错题状态

任何所有权字段变化、revision 失效、版本不匹配或候选冲突都会拒绝认知候选并回退普通 `QuestionPlan`。

## 5. 明确不做的事情

当前阶段不做：

- 不分析自由聊天、普通讲解、OCR 文档或未绑定知识点的内容。
- 不推断智力、性格、注意力、情绪稳定性或学习风格。
- 不创建第二套掌握度、复习时间或课程进度。
- 不绕过现有练习范围和 eligible topics。
- 不自动生成新的 hypothesis code。
- 不让 LLM 决定状态迁移、教学策略或诊断是否有效。
- 不向用户显示未经校准的概率、置信度和强度。
- 不建立单独的“认知孪生聊天页”或复杂认知大屏。
- 不训练新的基础模型。
- 不在 V2 中安排跨天学习时间。
- 不在 V2 中做教学策略个性化。
- 不允许 `hypothesized` 状态改变真实题目。
- 不同时激活多个学科或概念簇；知识图谱通用假设只能停留在 Shadow。
- 不扩展新的 Active 学科或错因；Active 仍只限链式法则 `omit_inner_derivative`。
- V3 只允许 Shadow 记录与离线策略效果归因；在线策略个性化保持关闭。
- 不建立通用工作流引擎或全局事件总线；事实顺序只服务认知域。
- 不展示概率、智力、注意力、学习风格或类似人格化判断。
- 不修改 N.E.K.O 核心仓库。
- 不因认知内部故障丢失或回滚正常答题。
- 不允许 retention 直接覆盖、提前或延后 FSRS 安排。

## 6. 首批学科和错误机制范围

### 6.1 概念簇

- 规范知识点 ID：`calculus.chain_rule`
- 仓库现有别名：`college_chain_rule`

别名只用于兼容现有课程数据，不会创建第二份知识点。证据始终保留真实答题绑定的 topic ID。

### 6.2 错误机制目录

| hypothesis code | 含义 | 当前可用性 |
|---|---|---|
| `omit_inner_derivative` | 求了外层导数，但遗漏内层导数 | Active 代码路径 |
| `differentiate_inner_incorrectly` | 使用了链式法则，但内层函数求导错误 | Shadow |
| `confuse_product_and_chain` | 混淆乘积法则与链式法则 | Shadow |

一次干预只能处理一个 hypothesis。其余错误机制必须分别积累标注样本、校准精确率并独立通过放行门槛后才能开启。

### 6.3 知识图谱通用 Shadow 目录

PR #81 在已审定的链式法则目录之外，增加了知识图谱驱动的通用 Shadow 层。只有 `store.get_topic(topic_id)` 能返回同 ID topic 的知识点才会进入目录；未知、已删除或读取异常的 topic 一律 fail-closed。

| hypothesis code | 含义 | 当前可用性 |
|---|---|---|
| `concept_misunderstanding` | 对目标知识点的定义、规则或概念关系理解错误 | Shadow |
| `prerequisite_gap` | 错误更可能来自知识图谱列出的前置知识缺口 | Shadow |
| `procedure_or_representation_error` | 概念可能已理解，但过程、转换、化简、记号或表示出错 | Shadow |

通用目录的约束：

- 已审定的链式法则 topic 继续使用专用闭集假设，不会被通用假设覆盖。
- 通用假设没有 Active code 和题目 blueprint，不能生成 probe、repair 或 transfer 干预题。
- topic context 只提供描述、前置知识、技能和典型误解等解释上下文，不能作为 support/counter 证据。
- `knowledge_graph_enabled = true` 只扩大 projection 开启后的 Shadow topic 范围，不能单独启动认知任务。

## 7. 总体架构

### 7.1 状态真相源

V2.0/V2.1 只保留三个逻辑层：

```text
不可变事实
    ↓
单一 reducer
    ├── evidence_status
    ├── intervention_stage
    └── monitoring episode
          ↓
Reader 实时叠加当前用户控制
```

事实、投影和控制不得相互冒充：旧 `status` 只作为兼容派生值，不参与任何判断；旧 `user_override` 列暂不删除，但新投影与 Reader 不依赖它。Reader 必须在读取时计算当前有效控制，因此 suppress 到期无需等待新 evidence 或新 projection 即可恢复。

单一 reducer 必须按认知专用 `root_fact_seq` 折叠 evidence、outcome 和 intervention 事实。迟到 evidence 继承源 attempt 的序号，evidence 与同 attempt 的 outcome 是原子事实包。不得先折叠全部 evidence、再用干预事件覆盖；否则旧 transfer 可能覆盖更新的 relapse。

### 7.2 选题与交付链路

```text
FSRS / Wrong Question / Learning Plan 候选
                    │
CognitiveStateReader → IntentPolicy → Cognitive 候选
                    │
                    ▼
           Coach Planner 单一决策
                    │
                    ▼
             最终 QuestionPlan
                    │
       ┌────────────┴────────────┐
       ▼                         ▼
    普通题              人工审定 Blueprint + Validator
                                  │
                     校验失败 ────┴──── 校验成功
                         │                  │
                         ▼                  ▼
                 同 topic 普通题        认知题
                         │                  │
                         └────────┬─────────┘
                                  ▼
                       服务端 Evaluator verdict
                                  │
             ┌────────────────────┼────────────────────┐
             ▼                    ▼                    ▼
          Mastery             错题 / FSRS       cognitive_outbox
         原所有者写入          原所有者写入              │
                                                       ▼
                                               不可变认知事实
                                                       │
                                                       ▼
                                                  单一 reducer
                                                       │
                                                       ▼
                                         cognitive_hypothesis_current
```

关键原则是单一 Planner 决策：各领域只提交候选，Coach Planner 统一决定知识点与最终行动。认知引擎只能对候选附加同一 topic 内的练习意图，不能在入口层二次选题或后置篡改计划。

`blocked_diagnostic` 仍然只表示前置知识就绪诊断，必须使用 `learning_intent="readiness_probe"`，不能复用为认知错因诊断，也禁止携带任何认知装饰。

PR #81 在提取前增加知识图谱校验与上下文装配：已审定 topic 走原专用目录；其余已验证图谱 topic 走三个通用 Shadow 假设。这个扩展发生在证据提取边界，不改变 Coach 的 topic selection，也不给通用假设增加干预蓝图。

## 8. 核心契约

### 8.1 LearningIntent

`SelectionReason` 回答“为什么选择这个知识点”，`LearningIntent` 回答“准备怎样教这个知识点”。两者不能合并。

当前意图集合：

- `practice`
- `readiness_probe`
- `misconception_probe`
- `misconception_repair`
- `transfer_check`
- `retention_check`

V2 Active 只使用：

- `misconception_probe`
- `misconception_repair`
- `transfer_check`

`retention_check` 保留给 V2.1。

### 8.2 HypothesisRef

`HypothesisRef` 是对一次确定投影结果的版本化引用，包含：

- hypothesis ID
- topic ID
- hypothesis code
- 状态
- 内部概率
- model version
- source snapshot / source attempt
- projection generation

Active 题必须引用具体 snapshot 和 generation。不能只传一段自然语言描述，也不能使用旧的 `misconception_target` 作为认知状态主键。

### 8.3 QuestionPlan 和 QuestionInstance

认知字段以兼容方式追加，旧构造方式默认得到普通练习：

- `learning_intent = "practice"`
- `hypothesis_target = None`
- `repair_strategy = ""`
- 认知 decision、validator 和 diagnostic validation provenance 默认为空

服务端 `QuestionInstance` 是答题提交时的可信来源。客户端公开 payload 不能自行伪造认知 provenance；topic 不匹配、字段缺失或绑定无效时会清除认知字段并按普通题处理。

V2.1 兼容追加：

- `obligation_refs`：一个题目可同时满足 FSRS、错题和认知 obligation，但最多绑定一个 cognitive hypothesis；
- `cognitive_strategy`：认知策略的通用字段；
- `repair_strategy`：只为旧数据兼容保留，不得把 retention 伪装成 repair。

### 8.4 LearningActionCandidate

候选行动只用于内部 Shadow 和后续统一决策：

- source
- topic ID
- intent
- urgency
- expected learning gain
- information gain
- evidence refs
- satisfies
- not before / due by / expires at
- obligation refs

它只是候选，不得直接写 FSRS、Mastery、课程计划或最终行动。

合并规则固定为：wrong retry 与 FSRS overdue 保持优先；retention 在 `due_by` 前只能与同 topic 任务顺带合并，超过 `due_by` 后可以成为 Coach 候选，但最终仍由 Coach 决定。

## 9. 数据模型

### 9.0 `cognitive_fact_roots` 与 `CognitiveVersionSet`

`cognitive_fact_roots` 是认知域专用的事实根，不扩展为全局事件系统。attempt、question、control 获得单调 `root_fact_seq`，并记录 `fact_type`、`effective_at`、`recorded_at` 与 `source_id`。迟到 extraction 复用源 attempt 的 root sequence，不按 worker 完成时间重排历史。

`CognitiveVersionSet` 是受支持版本组合的注册表，固定 catalog、extractor、reducer/projection、policy、blueprint 与 validator 的组合。第一组冻结名为 `cognitive-v2.1-1`。未知组合或任一组件不兼容时完全 fail-closed；不同 version set 使用独立投影，不能覆盖旧投影。

### 9.1 `cognitive_extraction_queue`

职责：管理证据提取任务。

关键特征：

- 主键为 `(attempt_id, extractor_version)`。
- 同一历史答题可以由新 extractor 重新处理。
- 支持 pending、processing、done、failed。
- 使用 lease token、retry count 和错误信息实现接管与故障隔离。
- 答题事务只负责入队，不在事务内调用 LLM。

旧 `cognitive_projection_queue` 仅作为 V1 兼容面保留。

### 9.2 `cognitive_evidence`

职责：保存不可变证据事实。

关键字段：

- attempt / topic / hypothesis code
- direction：support 或 counter
- strength
- extractor confidence
- diagnosticity
- source kind
- evidence span
- extractor version
- evidence family ID
- question ID
- session ID
- diagnostic validation ID

同一 attempt 对同一 hypothesis 和 extractor version 最多产生一个聚合结果，避免 LLM 输出多句话却被误算为多条独立证据。

`evidence_family_id` 和 `session_id` 用于防止同题重试、同模板变体或同一次普通练习会话被重复计算为独立支持证据。

### 9.3 `cognitive_hypothesis_snapshots`

职责：保存可重建的历史投影。

它用于审计、版本比较和全量重建一致性验证，不再承担“查询当前状态”的职责。

### 9.4 `cognitive_topic_projection_queue`

职责：管理按 topic 重建。

每个 topic/model version 维护：

- requested generation
- claimed generation
- projected generation
- status
- lease token
- retry count
- last error

提取器写入新证据时立即增加 requested generation。投影 worker 只能用 CAS 完成自己 claim 的 generation；如果重建期间 topic 再次变脏，新 generation 会继续保留，旧 worker 不得覆盖新状态。

### 9.5 `cognitive_hypothesis_current`

职责：保存 Reader 唯一可以读取的当前状态。

当前状态显式拆为：

- evidence status
- intervention stage
- monitoring episode 引用
- probability 和证据计数
- source snapshot / attempt
- model version
- projected generation
- 最近一次 intent/outcome
- 连续修复失败次数

Reader 不再从历史快照猜测哪条是最新状态。

旧 `status` 继续作为兼容派生值，旧 `user_override` 列暂时保留以支持 v0.2.5 回滚读取，但二者均不是新 reducer 的输入；当前用户控制由 Reader 实时叠加。

### 9.6 `cognitive_intervention_events`

职责：保存不可变干预账本。

事件只有四种：

- `intent_proposed`
- `question_committed`
- `attempt_committed`
- `intervention_abandoned`

事件记录 hypothesis 版本、题目、attempt、策略、课程计划和 scope revision、错题绑定、题目族、blueprint、policy version 与 validator version，但不重复保存原始答案。

生成题目不代表干预发生。只有 question committed 和后续 attempt committed 才能证明题目真正交付并作答；被替换、取消或失败的题必须记录 abandoned，不能推动状态机。

对于有效认知干预题，`attempt_committed` 与答题事实原子提交，避免出现“答案已写入但干预账本丢失”或相反的半提交状态。

`attempt_committed` 是终态，禁止再写 `intervention_abandoned`。同一 question commit 与 attempt commit 必须有唯一约束并保持幂等。

### 9.7 `cognitive_user_controls`

职责：保存用户对认知判断的最高优先级覆盖。

- dismiss：持续否认，直到 restore。
- suppress：暂不处理，存储层强制到期时间不超过创建后 24 小时。
- delete：删除认知派生数据，保留原始答题事实和永久 `delete_cutoff_seq`。
- restore：解除当前覆盖；只允许 cutoff 之后的新事实，不复活删除前事实或其迟到 extraction。

控制发生时必须使已提交但尚未作答的认知题失效；旧 worker 在控制之后提交时必须被 identity/CAS fence 拒绝。
从旧数据库迁移时，没有 `expires_at` 的历史 suppress 会转换为 dismiss，以保留原有的无期限抑制语义，同时不绕过新版本的 24 小时 suppress 上限。

### 9.8 `cognitive_outbox`

普通答题事务原子写入 attempt、Evaluator verdict、FSRS/Mastery/错题正常更新与引用型 `cognitive_outbox`。outbox 只保存服务端身份和 provenance 引用，不复制用户原始答案。认知 worker 的校验、投影或重试失败不会回滚普通答题；同一 outbox 项连续失败达到 5 次后转为 `discarded`，不再被 worker 领取。

### 9.9 `MonitoringEpisode` 与 `LearningObligation`

认证 transfer 成功时原子创建 `MonitoringEpisode`；每个 open episode 同时最多一个有效 retention `LearningObligation`。`ObligationClaim` 使用 token、独立短 lease 和 CAS，`ObligationSatisfaction` 独立记录最终完成。取消、超时、接管必须释放或终结 claim；dismiss、suppress、delete 必须原子取消或暂停相关 obligation。

completed obligation 与 projection generation 解耦，全量重建不得重复创建或再次满足已经完成的 obligation。
episode 到达保持窗口终点时，若最新用户控制仍是有效 suppress，则取消现有 obligation 并将 episode 标记为 expired，但不新建 transfer obligation；不得用窗口到期绕过用户抑制。

## 10. 证据提取和评分

### 10.1 输入限制

提取器只接受：

- 已绑定且能被审定目录或知识图谱存储验证的 QuestionInstance；
- 服务端保存的题目与标准答案；
- 学习者结构化答案；
- 服务端 EvaluationResult；
- 当前 topic 的 hypothesis 白名单。

对于知识图谱通用 Shadow topic，输入还可以包含服务端读取并经过 token budget 裁剪的 `topic_context`，用于解释知识点描述、前置知识、技能和典型误解。它不是学习者作答证据，不能单独形成 support 或 counter。

不接受自由聊天、普通讲解、OCR 内容或客户端自行提交的假设编号。

### 10.2 输出限制

- 最多返回三个 hypothesis evidence。
- hypothesis code 必须来自当前 topic 白名单。
- 必须提供答案中的 `evidence_span`。
- 证据不足时允许并鼓励返回空数组。
- 整批结构校验失败时整次提取失败，不写部分结果。
- LLM 不可用、超时或输出越界时安全失败，不影响普通题策略。

### 10.3 权重

内部可解释权重为：

```text
evidence_weight
= direction
× strength
× extractor_reliability
× question_diagnosticity
```

投影使用 log-odds：

```text
posterior = sigmoid(prior_logit + Σ support_weight - Σ counter_weight)
```

当前默认值：

- prior probability：0.55
- contradicted 阈值：小于 0.25
- supported 概率候选阈值：不低于 0.75
- 高质量诊断还必须同时满足权重、强度和提取置信度门槛

概率达到阈值仍不足以进入 supported，还必须满足下列之一：

- 至少两次独立普通支持证据；
- 一次经过认证的高质量诊断证据。

单次普通答错最多进入 `hypothesized`；单次普通答对不能直接解决误解。

内部概率只用于确定性投影和排序，V2 UI 不向用户展示概率。

## 11. 三层状态模型

### 11.1 证据状态

- `hypothesized`
- `supported`
- `contradicted`

### 11.2 干预阶段

- `idle`
- `probing`
- `remediating`
- `provisionally_resolved`
- `monitored`

数据库契约为后续版本保留 `resolved`；V2.0 的终点是 `monitored`，不会推进到该阶段，V2.1 才允许满足延迟、独立、无提示和认证条件的 `monitored → resolved` 转移。

### 11.3 用户覆盖

- 无覆盖
- `dismissed`
- `suppressed`
- `deleted`

用户覆盖优先于模型证据和干预阶段。

这里的“用户覆盖”是 Reader 在读取时叠加的当前控制，不是 reducer 投影字段。永久删除通过 `delete_cutoff_seq` 过滤事实；临时 suppress 到期后 Reader 立即恢复，不等待投影更新。

### 11.4 V2 主路径

```text
supported
    │
    ▼
misconception_probe
    │ 诊断确认
    ▼
misconception_repair
    │ 修复题成功
    ▼
provisionally_resolved
    │ 不同题族 transfer_check 成功
    ▼
monitored
```

回退规则：

- 诊断失败：回到 supported。
- 修复失败：保持 supported/remediating，允许同策略再尝试一次。
- 同一 session、同一修复策略连续失败两次：停止本次认知干预，回退普通练习。
- 迁移失败：回到 supported。
- monitored 后再次出现支持该错因的新证据：回到 supported，并增加 relapse count。
- 用户否认或删除：立即停止干预。

### 11.5 V2.1 固定时间合同

全部时间从“认证 transfer 成功”开始计算：

| 字段或限制 | 固定值 |
|---|---|
| `not_before` | 24 小时 |
| `due_by` | 72 小时 |
| `eligibility_until` | 7 天 |
| retention 频率 | 同 hypothesis 每滚动 24 小时最多一次 |
| 复发后冷却 | 24 小时 |
| worker lease | 独立短期超时，不复用 `eligibility_until` |

超过 7 天仍未完成有效保持检查时，episode 变为 `expired`，`intervention_stage` 回到 `provisionally_resolved`，并通过 Coach 候选重新安排 `transfer_check`。该情况不会自动 `resolved`，也不计为 relapse；若到期时存在有效 suppress，则不创建新的 transfer obligation。

### 11.6 Retention 结果矩阵

| 结果 | 状态变化 |
|---|---|
| 延迟、独立、无提示、认证题正确 | `monitored → resolved` |
| 形成同一 hypothesis 的 support evidence | `→ supported`，并增加 `relapse_count` |
| 错误属于其他机制 | 保持 `monitored`，在窗口内重排 |
| `partial` / `dont_know` | 保持 `monitored`，在窗口内重排 |
| 提前、重复题族、版本不兼容 | 只作为普通 evidence，不完成 obligation |
| 错过 `eligibility_until` | episode `expired`，回到 `provisionally_resolved`；无有效 suppress 时重新 transfer |

错误答案不等于 relapse；只有同一 hypothesis 的 support evidence 才触发复发。认证 retention observation 必须包含 `used_hint`、Evaluator 类型/版本/confidence、episode/obligation、时间窗认证和 blueprint/validator 版本。

## 13. 诊断、修复和迁移题

V2 使用人工审定的链式法则蓝图：

- 正误步骤对比；
- 补全遗漏步骤；
- 乘积结构与复合结构辨析；
- 最小变化题；
- 不同表达形式的迁移题。

LLM 最多改变自然语言表述，不得改变：

- 数学结构；
- 标准答案；
- 目标 hypothesis；
- 竞争 hypothesis；
- diagnostic signature；
- question family；
- 原计划的所有权字段。

DiagnosticQuestionValidator 必须验证：

- topic 未变化；
- 标准答案与 blueprint 一致；
- 能区分目标与竞争假设；
- 不泄露答案；
- transfer 与 repair 不属于同一题族；
- plan、scope、revision 和错题绑定仍有效；
- validator、blueprint 和 diagnostic validation provenance 完整。

每个 retention blueprint 必须携带与自身题型一致的 `key_points` 和 `solution_steps`。题族轮换后不得沿用另一题族的讲解内容，最终 payload 仍需通过 blueprint 一致性校验。

验证失败时：

- 不交付该认知题；
- 不获得高诊断权重；
- 不推动干预状态；
- 回退原普通题。

## 14. Reader 与一致性

CognitiveStateReader 采用 fail-closed 读取：

1. 读取 topic projection generation。
2. 读取 current hypotheses 与用户控制。
3. 再次读取 generation。
4. 只有前后 generation 一致，且 requested generation 等于 projected generation，才返回认知状态。

以下任一情况返回空认知状态：

- 存在尚未处理的新证据；
- topic 正在重建或重建失败；
- 前后读取期间 generation 变化；
- model、extractor、catalog 或 projection 版本不匹配；
- suppression 尚未到期；
- 数据结构异常；
- topic 不受支持。

返回空状态意味着继续普通练习，而不是阻塞答题或猜测旧状态。

## 15. 后台任务与生命周期

认知后台任务复用现有伴学生命周期管理：

- 答题成功、question committed、intervention abandoned 和用户 control 后请求投影任务。
- 同一时间只保留受控 worker，重复请求合并为 dirty replay。
- 提取和 SQLite 投影工作不占用同步答题 LLM 路径。
- lease 过期后允许新 worker 接管。
- 旧 worker 通过 token/generation CAS fencing，不能清理或覆盖接管者状态。
- 插件关闭时停止新任务，并有界等待或安全结束后台任务。
- 题目生成后发生异常或取消时，以 bounded、cancel-safe 的方式补写 abandonment。
- retention obligation 已领取但题目准备或校验异常时，必须 best-effort 释放对应 claim 并回退普通题。
- 未作答 Active 题被替换时，如果无法确认 abandonment，选择 fail-closed，不继续交付新的认知题。

### 15.1 答题异常分类

| 异常 | 普通答题 | 认知效果 |
|---|---|---|
| 客户端伪造 provenance，或 question/attempt/topic 身份错配 | 拒绝请求 | 不记录 |
| 内部认知校验、投影或 worker 故障 | 正常提交 | outbox 标记失败或等待重试 |
| 整体 SQLite / 磁盘事务故障 | 整个事务失败 | 与事务一起失败 |
| stale obligation / control | 正常提交 | 丢弃认知效果 |

“内部认知故障不丢正常答题”不意味着吞掉存储故障，也不放宽客户端身份校验。普通答题事务必须保持 attempt、Evaluator verdict、FSRS、Mastery、错题更新和 outbox 的原子性；后续认知处理独立重试。

## 17. 配置、灰度与回滚

```toml
[cognitive]
projection_enabled = false
read_mode = "off"          # off / shadow / active
intent_policy = "off"      # off / shadow / on
ui_enabled = false
retention_enabled = false
knowledge_graph_enabled = true
version_set = "cognitive-v2.1-1"
supported_topics = ["calculus.chain_rule", "college_chain_rule"]
```

高级设置中的三个简化模式映射为：

| 设置模式 | projection | read | intent | UI | retention |
|---|---:|---|---|---:|---:|
| Off | false | off | off | false | false |
| Shadow（兼容保留） | true | shadow | shadow | false | false |
| Active V2.0 | true | active | on | true | false |
| Active V2.1 | true | active | on | true | true |

V2.0 主动干预只有在 `projection_enabled=true`、`read_mode="active"`、`intent_policy="on"` 同时成立时生效。V2.1 还必须满足 `retention_enabled=true`。运行时仍保持硬约束：projection 未启用或 read 为 off 时，intent 强制为 off；intent 请求 on 但 read 不是 active 时只按 shadow 执行。`knowledge_graph_enabled` 只控制已验证图谱 topic 是否加入非 Active 证据范围，不会让通用假设进入 Active。

任何未知 version set、组件版本不匹配、投影积压、stale episode 或 obligation 冲突都回退普通 `QuestionPlan`。

### 17.1 本轮放行决定

用户明确决定跳过连续 7 天真实 Shadow、Read Only、Personal Beta 和 `ACTIVE_LOCAL` 的等待阶段，直接按默认关闭的功能开关实施 V2.0/V2.1。历史 Shadow 模式和报告继续保留作回归工具，但不再是合并或版本发布的前置门槛。

该决定只取消等待阶段，不改变以下要求：

- 所有功能默认关闭，全部关闭时与 v0.2.5 正常学习行为等价；
- Active 只允许链式法则 `omit_inner_derivative`；
- 所有权、版本、身份或状态不明确时回退普通题；
- 定向覆盖事实乱序、删除 cutoff、控制即时性、worker 接管、故障隔离、obligation 幂等和 Web/Electron 共用 UI；
- 不声称对不同用户普遍有效。

### 17.2 回滚顺序

1. `intent_policy = "off"`
2. `retention_enabled = false`
3. `read_mode = "off"`
4. `ui_enabled = false`
5. 必要时 `projection_enabled = false`

数据库变更只允许 additive migration，不删除 v0.2.5 列和表。新 reducer 使用独立 version set，不覆盖旧投影。回滚功能时不删表、不删原始答题事实；永久 `delete_cutoff_seq` 也不得被旧代码绕过。

关闭 `retention_enabled` 后立即停止产生和消费新的 retention obligation。关闭 intent 后仍保存普通答题和符合边界的 evidence，但不交付认知题。outbox 积压不得阻塞普通答题。

### 17.3 一次即回滚的条件

- 修改了 Coach 原选知识点；
- 使用失效 plan/scope revision；
- 丢失错题绑定；
- 修改 FSRS、Mastery、课程进度或错题状态；
- 用户否认、暂缓或删除后仍继续干预；
- 错误诊断题被实际交付；
- 认知异常阻塞普通答题；
- stale 或版本不匹配状态被 Active 使用。

## 19. 历史质量指标与当前验收

以下 Read Only、Personal Beta、`ACTIVE_LOCAL` 指标来自原真实 Shadow 灰度方案，继续作为观察指标和未来校准参考，但用户已明确跳过这些等待阶段；它们不再阻塞 V2.0/V2.1 的工程实施。本轮工程硬验收改为：冻结状态迁移无歧义、定向故障与并发用例通过、所有开关默认关闭、关闭等价、未知状态 fail-closed、Active 范围不扩大。最终真人实测被有意放在工程可观测性和自动化闭环验收之后，用于补齐真实有效性证据，不恢复为此前的 7 天发布阻塞门槛。

### 19.1 进入 Read Only

- 投影与全量重建一致率：100%。
- supported 假设人工精确率：至少 90%。
- evidence span 忠实率：至少 95%。
- 非法输出落库：0。
- 用户控制全部有效。

若未来恢复真实用户校准，这些指标必须来自真实用户数据和人工复核。链式法则 22 条审定样本的 100% 初评不能证明通用有效，知识图谱通用假设也不能借用该结果获得 Active 资格。

### 19.2 进入 Personal Beta

- 本地 Shadow 连续运行至少 7 天。
- 至少 30 次有效结构化答题。
- 至少覆盖 10 个题目族。
- 所有真实 supported 判断逐个复核。
- 诊断题区分有效率至少 95%。
- 实际交付错误诊断题：0。
- 答题提交 p95 延迟增量不超过 5ms。
- 必须由用户主动开启。

### 19.3 进入 ACTIVE_LOCAL

- 至少完成 5 个完整干预闭环。
- 至少 4 个通过迁移验证。
- 用户否认 supported 判断数为 0。

知识图谱通用假设当前没有 Active blueprint，因此即使未来达到 Read Only 指标，也不会自动获得 Personal Beta 或 ACTIVE_LOCAL 资格；若要主动干预，必须另行审定 topic-specific hypothesis、题目蓝图和独立放行门槛。

## 21. V2.1：跨天保持与最终解决

### 21.1 目标

V2.1 只负责回答：

> 迁移题已经成功后，这个错因能否在跨天间隔后仍然不再出现？

### 21.2 已实现能力

- 为 `monitored` 假设产生 `retention_check` 候选。
- 提供 `not_before`、`due_by` 和 intent，不直接写 FSRS 时间。
- 通过持久化 `LearningObligation`，让一次题目可以同时满足：
  - FSRS 到期复习；
  - 认知保持检查；
  - 错题迁移验证。
- 最终时间仍由 Coach Policy 合并决定。
- 高质量延迟保持成功后，允许 `monitored → resolved`。
- 只有同一 hypothesis 的新 support evidence 才回到 `supported` 并增加 relapse count；其他错误、`partial` 与 `dont_know` 只在窗口内重排。

### 21.3 V2.1 仍然不做

- 不改变知识点选择权。
- 不覆盖 FSRS due time。
- 不把一次短期答对视为保持成功。
- 不做个性化策略选择。
- 不扩展新学科或新 Active 错因。

### 21.4 已冻结的 V2.1 决策

- 时间窗为 transfer 后 24 小时至 7 天：`not_before=24h`、`due_by=72h`、`eligibility_until=7d`。
- wrong retry 与 FSRS overdue 优先；retention 在 `due_by` 前只允许同 topic 顺带合并，逾期后可成为 Coach 候选。
- 只有人工审定 blueprint、独立性分组不同、无提示且版本兼容的认证题可以完成 obligation。
- 同 hypothesis 每滚动 24 小时最多一次 retention；复发后冷却 24 小时。
- `CognitiveVersionSet` 明确版本组合；不兼容结果仅作为普通 evidence，不能完成 obligation。
- 超过 7 天未完成时 episode 过期，回到 `provisionally_resolved` 并重新 transfer，不自动 `resolved`、不算 relapse。

## 22. V3：教学策略个性化

### 22.1 目标

V3 只在同一知识点、同一已确认 hypothesis 内比较不同修复策略的效果，例如对比：

- 正误步骤对比；
- 补全步骤；
- 最小变化；
- 结构辨析；
- 不同表示形式。

### 22.2 边界

- 不根据性格、智力或学习风格选择策略。
- 不获得 topic selection 所有权。
- 不把短期做对当成策略长期有效。
- 不允许 LLM 自由发明策略。
- 只能从人工审定、版本化的策略目录中选择。
- Coach Policy 仍然可以拒绝认知策略候选。

### 22.3 前置条件

- V2.1 的跨天 outcome 已可靠记录。
- 每种策略有足够的独立干预样本。
- 能区分题目难度、题族和策略本身的影响。
- 具备探索上限、连续失败停止、用户停止和全局回滚机制。
- 离线回放证明不会改变知识点、复习时间和课程范围。

V3 在这些条件满足前只允许 Shadow 比较，不允许自动个性化。

### 22.5 V3-PR1 exposure 与离线报告冻结合同

**Exposure 创建与幂等：**

- exposure 表示用户实际收到的一道、带已审定策略版本的题，不表示 Shadow 推荐但未交付的候选。只有包含有效 `strategy_id`、`strategy_version`、`catalog_version` 和 `version_set_id` 的 `question_committed` 创建 exposure；`attempt_committed` 只把结果绑定到既有 exposure，不能创建第二条 exposure。
- `exposure_id` 固定为 `cognitive-strategy-exposure:{sha256(canonical_json([question_id,strategy_id,strategy_version,catalog_version,version_set_id]))}`，其中 canonical JSON 使用 UTF-8、固定字段顺序和无多余空白编码。同一 `question_committed` 重放必须得到相同 ID 并幂等合并；任何实际提交的新 question 都使用新 `question_id`，即使题族或策略相同也创建新 exposure。
- 用户放弃的 question 保留 exposure 并标记 `abandoned`；被替换的旧 question 标记 `replaced` 并记录新 `replacement_exposure_id`，替换后的 question 创建新 exposure；同一 question/attempt 的事务重试只重放原 exposure 和结果。禁止删除这些记录或把 abandoned、replaced、retried 合并成一次成功曝光。
- exposure 必须保留创建时的 topic、hypothesis、episode、question family、difficulty、提示状态、Planner/Coach 决策、blueprint/validator/evaluator provenance 和 root fact/version set；后续目录或模型升级不得改写历史值。

**报告纳入、窗口与缺失处理：**

- 报告以固定 `as_of_root_fact_seq`、`catalog_version` 和完整 `version_set_id` 为输入边界。实际 exposure 的目录项必须有效，策略必须在 `question_committed` 前确定，且 question、attempt 与 outcome 的 root fact/provenance 链完整；不兼容版本、无认证 evaluator、迟到越过冻结窗口或链路不完整的记录按固定 reason code 排除并单独计数。
- immediate outcome 取该 exposure 在 `answer_window_expires_at` 前的唯一认证 `attempt_committed`；transfer outcome 取同一 episode 中认证 `transfer_check` 的冻结答题窗口结果；retention outcome 只取 transfer 后 `24h ≤ interval ≤ 7d`、独立题族、无提示且完成 obligation 的认证结果。三个 endpoint 分开报告，不用短期答对替代 transfer 或 retention。
- 截止 `as_of_root_fact_seq` 仍未到窗口终点的 exposure 标记为右删失 `pending`；窗口结束后没有认证结果的标记为 `missing_outcome`；`abandoned` 与 `replaced` 保持各自状态。它们进入曝光量、完成率和缺失敏感性分析，但不进入主要效果分子的成功数，也不静默按成功或失败插补。
- 主要效果表只比较同一 topic、hypothesis、question family、difficulty bucket、提示状态和 version set 的共同分层；策略目录必须为每个比较范围和版本指定且仅指定一个 `baseline=true` 的基线策略。同一 learner、hypothesis、episode、strategy 和滚动 24 小时窗口内只把 root sequence 最早的合格 exposure 计为独立样本，其余仍计入曝光量但不进入效果估计。每个策略输出固定顺序的 `eligible_n`、`success_n`、`success_n / eligible_n` 与确定性 Wilson 95% 区间；只有同一分层内每个待比较策略至少 20 个独立 exposure 时才计算差值，否则标记 `insufficient_data`。
- 分层综合差值使用共同合格 exposure 数形成的固定权重：`weight_s = eligible_n_s / Σ eligible_n_s`，`effect = Σ weight_s × (rate_strategy_s - rate_baseline_s)`。同时输出把全部 `missing_outcome` 分别视为失败和成功的上下界；该结果只描述观察关联，不作为因果结论，也不能驱动在线策略切换。
- 重放按 `(root_fact_seq, source_id, exposure_id)` 稳定排序并按 `exposure_id` 去重；计数和权重先用整数/有理数计算，展示时统一四舍五入到 6 位小数。报告生成时间不参与内容摘要，所有状态均相对于 `as_of_root_fact_seq` 推导，因此相同事实、目录版本和 version set 必须生成字节稳定的 canonical JSON 与相同摘要。

## 24. 运维与故障处理

### 24.1 投影积压

1. 保持 intent policy 关闭或 Shadow。
2. 检查 failed extraction 和 topic queue。
3. 回收过期 lease。
4. 修复 extractor 后使用新 version 重跑。
5. 按 topic 全量重建并核对 generation。
6. 只有 current 与 requested generation 一致后才允许读取。

### 24.2 错误判断

1. 立即关闭 intent policy。
2. 对相关 hypothesis 写 dismiss 或 delete。
3. 保留原始 attempt 以便审计。
4. 复核 evidence span、题目 diagnosticity 和 family 去重。
5. 如属 extractor 缺陷，升级 extractor version，不覆盖旧证据。

### 24.3 错误诊断题被交付

1. 立即关闭 intent policy。
2. 标记并停止对应 blueprint/version。
3. 检查 validator 和服务端 provenance 边界。
4. 对所有使用该 validation/version 的事件做影响分析。
5. 修复后只跑相关定向回归和离线回放，再恢复 Shadow。

### 24.4 用户请求删除

1. 在认知事实时间线写入永久 `delete_cutoff_seq`，并清除或隐藏 cutoff 覆盖的派生 evidence、snapshot 和 current 状态。
2. 保留原始答题事实。
3. 原子取消相关认知题、episode obligation 与有效 claim。
4. 后续全量重建和回滚代码都必须应用 cutoff，不得自动恢复已删除判断。
5. restore 只允许删除之后的新 root fact；删除前 attempt 的迟到 extraction 仍在 cutoff 之前，不得复活。
